# 0005. 문서는 성격별로 나누고, 공유 문서는 서버를 정본으로 둔다

- **상태**: 채택
- **날짜**: 2026-08-18
- **관련**: `../README.md`, `pacer_app` 이슈 #19

## 배경

두 저장소가 독립적이라 문서를 어디에 둘지 규칙이 없었고, 두 가지 문제가 드러났다.

1. **`Pacer_기획서_v1.md`가 양쪽에 중복.** 지금은 내용이 같지만 한쪽만 고치는 순간 드리프트가 시작되고, 어느 쪽이 맞는지 알 방법이 없다
2. **성격이 다른 문서가 한 디렉토리에 섞임.** ERD·API 명세(항상 현재 상태로 갱신)와 LLM 비용추정(그 시점의 판단 근거)이 나란히 놓여 있다

`Pacer/` 최상위는 git 저장소가 아니라 공통 문서를 둘 곳으로 쓸 수 없다.

## 결정

문서를 **세 종류**로 나눈다.

| 종류 | 위치 | 규칙 |
|------|------|------|
| 스펙 (ERD·API명세·화면정의서 등) | 구현하는 레포의 `docs/` | 코드와 같은 PR에서 바뀐다 |
| 공유 (기획서·MVP범위) | **`pacer_server/docs/` 정본**, 앱은 링크만 | 사본을 만들지 않는다 |
| 결정 기록 | `pacer_server/docs/decisions/` | 시점 스냅샷, 나중에 고치지 않는다 |

## 근거

**공유 문서를 서버 정본으로:** 어느 쪽도 자연스럽진 않지만 `Pacer_MVP범위_v1.md`가 이미 서버에만 있고,
상위 `CLAUDE.md`의 "서버 API 선개발 → 앱 연동" 순서와 맞는다.
무엇보다 **정본이 하나면 어디를 고칠지 고민할 일이 없어진다.**

**결정 기록을 분리:** 스펙은 갱신되고 ADR은 갱신되지 않는다. 갱신 규칙이 정반대인 문서를
한 디렉토리에 두면 둘 다 관리가 흐트러진다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
|------|-----------|
| 별도 `pacer_docs` 레포 | 1인 개발에서 레포 3개는 관리 비용만 늘어난다. 팀이 커지면 그때 승격 |
| GitHub Wiki | **PR 리뷰를 타지 않는다.** 계약 문서를 리뷰 없이 고칠 수 있는 건 위험하고, diff 추적도 약하다 |
| Notion / Confluence | 코드와 동기화가 끊긴다. 스펙이 코드와 어긋나도 아무도 모른다 |
| 현행 유지(양쪽 중복) | 드리프트가 시간 문제다. 지금 같은 건 아무도 안 건드렸기 때문일 뿐 |

## 따라오는 결과

- `pacer_app/docs/Pacer_기획서_v1.md`를 삭제하고 README에 서버 링크를 남긴다 (`pacer_app` #19)
- 앱 `CLAUDE.md`의 설계 문서 목록도 서버 링크로 수정한다
- 새 결정은 `decisions/`에 ADR로 쓴다. 판단 기준은 `decisions/README.md`
- 팀이 커지면 공유 문서를 별도 레포로 승격하는 안을 재검토한다
