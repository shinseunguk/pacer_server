# 0002. 브랜치 전략은 GitHub Flow

- **상태**: 채택
- **날짜**: 2026-08-14
- **관련**: 상위 `Pacer/CLAUDE.md` §4

## 배경

`pacer_app` / `pacer_server` 두 독립 저장소의 브랜치 전략을 정해야 했다.
후보는 GitHub Flow(`main` + 짧은 기능 브랜치)와 Git Flow(`develop` / `release` 추가)였다.

## 결정

**GitHub Flow** — `main`(항상 배포 가능) + 짧은 기능 브랜치 + 버전 태그.
`develop` / `release` 브랜치는 두지 않는다.

- 브랜치명: `<타입>/#<이슈번호>-<영문-슬러그>`
- 머지 방식: **Rebase and merge** (squash 아님), 머지 후 원격 브랜치 삭제
- `main` 직접 커밋 금지
- 릴리스는 태그(`v1.0.0`)로

## 근거

- **1인 개발이고 릴리스 열차가 없다.** `develop`을 둬도 `main`과 거의 같은 상태로 유지되기만 하고, 머지 지점만 하나 더 늘어난다
- Phase A는 클로즈드 베타라 **핫픽스와 기능 개발을 분리할 이유가 없다**
- Rebase를 고른 이유: 이슈 하나에 커밋 여러 개가 의미 있게 나뉘는 경우(예: 구현 + 테스트 + 문서)를 squash가 뭉개버린다. 히스토리에서 각 커밋의 의도를 남기고 싶다

## 따라오는 결과

- 기능은 반드시 이슈 → 브랜치 → PR → `main` 경로를 탄다
- `main`은 항상 배포 가능해야 하므로 **CI(lint/build/test)가 PR 게이트**가 된다
- 팀이 커지거나 릴리스 주기가 생기면 Phase B에서 `develop` 승격을 재검토한다
