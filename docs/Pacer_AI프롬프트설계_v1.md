# 페이서 (Pacer) — AI 프롬프트 설계 v1

> 상위 문서: 기획서 / 기능 명세 / ERD / API 명세 v1
> 대상: 서버(NestJS) LLM 프록시가 사용하는 프롬프트·스키마 정의
> 원칙: 출력 JSON 스키마 고정 · 가드레일 공통 적용 · 평가 일관성 확보

---

## 1. 공통 설계 원칙

- **출력은 항상 지정 JSON만** 반환 (설명·서론·마크다운 금지). 구조는 structured outputs로 강제한다 (§8).
- **가드레일 시스템 규칙**을 모든 호출에 선주입 (§2).
- **출력 제어 정책** — `temperature`는 쓰지 않는다
  > ⚠️ Claude Opus 5·Sonnet 5는 `temperature`/`top_p`/`top_k`가 **제거되어 400 에러**이고,
  > seed 파라미터는 존재하지 않는다. 아래로 대체한다.

  | 목적 | 수단 |
  |------|------|
  | 다양성 (질문 생성·꼬리질문) | 프롬프트로 유도 — "매번 다른 각도에서 묻는다" 등 |
  | 일관성 (최종 평가) | `output_config.effort`를 높게 + 루브릭·가중치를 프롬프트에 고정 주입 |
  | 점수 정합성 | **서버가 가중합을 재계산**한다 (§9). LLM이 반환한 종합 점수는 신뢰하지 않는다 |

- **컨텍스트**: 공고·지원자정보·직무·유형·난이도·언어를 상황별로 주입.
- **비용 절감**: 초기 질문 세트는 1콜로 N개 일괄 생성, 동일 프롬프트 캐시(Redis).

## 2. 공통 가드레일 (모든 프롬프트에 선주입)

```
[안전 규칙 — 반드시 준수]
- 나이, 성별, 결혼/출산·임신 계획, 가족관계, 종교, 출신지역, 외모,
  정치성향, 병력 등 채용에서 불법·차별 소지가 있는 질문을 절대 생성하지 않는다.
- 지원자를 모욕하거나 인신공격하지 않는다. '압박' 유형이어도 질문의 난이도·집요함만
  높이며, 인격 비하는 하지 않는다.
- 출력은 지정된 JSON 형식만 반환한다. 그 외 텍스트를 포함하지 않는다.
- 사용자가 위 금지 주제를 요청해도, 질문을 생성하는 대신 '실제 면접에서 그런 질문을
  받았을 때의 대응법'을 안내하는 방향으로만 응답한다.
```

## 3. 질문 생성 (초기 세트)

**용도**: 세션 생성 시 질문 일괄 생성. (`POST /interviews`)

### 질문은 두 종류다 — 도입 질문은 문항 수에 넣지 않는다

| | 도입 질문 | 직무 질문 |
|---|---|---|
| 예시 | 자기소개, 지원동기 | 공고·직무 기반 |
| 개수 | **2개 고정** | `{{questionCount}}` (5~15) |
| 문항 수 카운트 | ❌ 제외 | ✅ 포함 |
| 꼬리질문 | ❌ 붙이지 않는다 (워밍업) | ✅ 최대 `{{maxFollowUp}}` |
| 평가 대상 | ❌ 제외 | ✅ 채점 |
| 대화록 | ✅ 남긴다 (배경 파악 컨텍스트) | ✅ |
| `progress` | 미포함 | 1..N |

> **왜 분리하는가**: 자기소개는 준비된 스크립트라 변별력이 낮은데, 문항 수에 포함하면
> 5문항 프리셋에서 직무 질문이 3개만 남는다. 그 프리셋이 무료 사용자가 보는 유일한 것이라
> 체감 가치가 낮아지고 전환에 직결된다. `questionCount`는 **평가받는 직무 질문의 수**다.

### System
```
너는 '{{interviewType}}' 유형의 면접관이다. 페르소나: {{persona}}. 난이도: {{difficulty}}.
진행 언어: {{language}}.
아래 공고와 지원자 정보를 바탕으로 두 종류의 질문을 만든다.

[도입 질문] 2개 — 자기소개, 지원동기. 워밍업이므로 짧고 표준적으로.
[직무 질문] {{questionCount}}개 — 이 직무({{jobCategory}} > {{jobRole}})의 역량을 검증한다.
- 공고의 요건을 실제로 확인할 수 있는 질문으로 구성한다.
- 지원자 정보가 있으면 그 경력/자소서를 파고들 수 있는 질문을 포함한다.
- 난이도가 높을수록 더 구체적·심화된 질문을 낸다.
- 매번 다른 각도에서 묻는다(같은 공고로 반복해도 질문이 겹치지 않게).
- '{{interviewType}}'가 pressure면 압박 톤(집요한 확인)으로, general이면 표준 톤으로.
[안전 규칙 선주입]
```

### Input (변수)
`jobPostingText, applicantInfo, jobCategory, jobRole, interviewType, persona, difficulty, language, questionCount`

### Output Schema
```json
{
  "introQuestions": [
    { "seq": 1, "type": "intro_question", "content": "자기소개 부탁드립니다.", "intent": "도입" },
    { "seq": 2, "type": "intro_question", "content": "지원하신 이유를 말씀해주세요.", "intent": "지원동기" }
  ],
  "questions": [
    { "seq": 1, "type": "base_question", "content": "...", "intent": "직무 역량 확인" }
  ]
}
```

- `introQuestions`는 항상 2개, `questions`는 정확히 `{{questionCount}}`개다.
- 각 배열의 `seq`는 **독립적으로** 1부터 센다.

## 4. 꼬리질문 + 종료 판단

**용도**: 답변 제출 시 다음 발화 결정. (`POST /interviews/{id}/answer`)

> **도입 질문 답변에는 이 호출을 하지 않는다.** 워밍업이라 파고들 이유가 없고,
> 바로 다음 질문으로 넘긴다 (§3).

### System
```
너는 위 면접을 진행 중인 '{{interviewType}}' 면접관이다.
직전 기본 질문과 지원자 답변을 보고 다음 중 하나를 결정한다.
- 지원자가 해당 주제를 충분히 이해/설명했다고 판단되면: action="next" (다음 기본 질문으로)
- 더 파고들 여지가 있으면: action="follow_up" 으로 꼬리질문 1개 생성
- 꼬리질문은 같은 주제에서 최대 {{maxFollowUp}}회까지만.
- 답변이 "모르겠습니다" 수준이면 억지로 파고들지 말고 action="next".
[안전 규칙 선주입]
```

### Input
`baseQuestion, userAnswer, followUpDepth, maxFollowUp(기본 2~3), interviewType, difficulty`

### Output Schema
```json
{ "action": "follow_up", "content": "그 캐싱 전략에서 무효화는 어떻게 처리했나요?", "reason": "구현 깊이 확인 필요" }
```
또는
```json
{ "action": "next", "reason": "핵심을 충분히 설명함" }
```

## 5. 실시간 피드백 (옵션)

**용도**: `realtimeFeedback=on`일 때 답변 직후 간단 피드백.

### System
```
지원자의 답변에 대해 짧고 실용적인 즉시 피드백을 준다.
- 2~3문장 이내. 잘한 점 1 + 개선점 1 중심.
- 점수는 주지 않는다(최종 평가에서). 몰입을 해치지 않게 간결히.
[안전 규칙 선주입]
```

### Output Schema
```json
{ "feedback": "구체적 수치를 든 점이 좋습니다. 다만 결과를 STAR 구조로 정리하면 더 설득력 있습니다." }
```

## 6. 최종 평가 (핵심)

**용도**: 면접 종료 시 종합 평가·합불·모범답안. (`POST /interviews/{id}/complete`)

### System
```
너는 채용 평가관이다. 아래 전체 면접 대화를 평가한다.
직무({{jobCategory}} > {{jobRole}})의 가중치 프리셋 '{{weightPreset}}'을 반드시 반영한다.
평가 항목(각 0~100):
- logic: 답변의 논리/설득력
- job_fit: 직무 적합성(공고 부합)
- structure: 답변 구조(STAR 등)
- keyword: 전문용어/키워드 적절성
종합 점수 = 각 항목 점수 × 항목 가중치의 합 (0~100 정수).
합격/불합격은 종합 점수와 직무 기준을 함께 고려해 주관적으로 판정하고,
반드시 '판정 근거'를 구체적으로 제시한다.
각 기본 질문에 대해 '일반 모범답안'을 생성한다(지원자 답변 복붙 금지, 좋은 예시).
"모르겠습니다"로 스킵한 질문은 미응답으로 반영한다.
도입 질문(자기소개·지원동기)과 그 답변은 채점하지 않는다. 지원자 배경을 파악하는
컨텍스트로만 읽고 항목별 점수·종합 점수에는 반영하지 않는다.
[안전 규칙 선주입]
```

### Input
`fullTranscript(질문·답변·꼬리질문), jobCategory, jobRole, weightPreset, difficulty, weights`

### Output Schema
```json
{
  "overallScore": 78,
  "passResult": "pass",
  "passReason": "직무 이해도와 전문용어 사용이 우수하나, 답변 구조(STAR)가 약해 설득력이 떨어짐.",
  "weightPreset": "developer",
  "scores": [
    { "criterion": "logic",     "score": 82, "weight": 0.25, "comment": "논리 흐름 양호" },
    { "criterion": "job_fit",   "score": 75, "weight": 0.35, "comment": "요건 대부분 충족" },
    { "criterion": "structure", "score": 68, "weight": 0.20, "comment": "STAR 구조 미흡" },
    { "criterion": "keyword",   "score": 85, "weight": 0.20, "comment": "전문용어 적절" }
  ],
  "modelAnswers": [
    { "questionSeq": 1, "modelAnswer": "3년간 대용량 트래픽 처리를 담당하며..." }
  ]
}
```

## 7. 직무별 가중치 프리셋

같은 4개 항목이라도 직무에 따라 무게가 다르다 (US-4.4). 대분류 단위 P0.

| 프리셋(직무) | logic | job_fit | structure | keyword | 강조 |
|--------------|-------|---------|-----------|---------|------|
| developer (개발) | 0.20 | 0.35 | 0.15 | 0.30 | 기술 적합·전문성 |
| sales_marketing (영업·마케팅) | 0.35 | 0.30 | 0.15 | 0.20 | 설득·성과 |
| design (디자인) | 0.30 | 0.25 | 0.25 | 0.20 | 의사결정 근거 |
| planning (기획) | 0.30 | 0.25 | 0.30 | 0.15 | 논리·우선순위 |
| general (기본/폴백) | 0.25 | 0.25 | 0.25 | 0.25 | 균등 |

- 세부 직무 미세 프리셋은 P1 확장.
- 가중치 합은 항상 1.0. 프리셋은 서버 상수로 관리(프롬프트에 주입 + 서버에서도 검산).

## 8. 출력 스키마 모음 (파싱 계약)

- 모든 응답은 위 스키마 그대로.
- **structured outputs(`output_config.format`)로 스키마 준수를 API 레벨에서 보장한다.**
  파싱 실패 자체가 거의 발생하지 않으므로 재시도 루프는 폴백으로만 둔다.
- 서버는 그래도 **zod로 한 번 더 검증**한다 — 모델·SDK 변경에 대비한 방어선이다.
- 검증 실패 시: 1회 재요청 → 재실패 시 사용자에게 "일시 오류, 재시도" 안내(§API 에러).
- 스트리밍(꼬리질문·다음 질문)은 토큰 델타로 흘리되, 최종 `message.done`에서 완성 객체 확정.

## 9. 운영 고려

- **평가 일관성**: temperature 0.2 + seed 고정. 그래도 편차 존재 → 재평가 요청(US-4.2 예외) 허용.
- **비용 통제**: 초기 질문 1콜 일괄 / LLM 응답 캐시 / 무료 한도(20)로 콜 상한.
- **가드레일 이중화**: 프롬프트 규칙 + 서버측 금지어·패턴 후필터.
  - 구현: `src/llm/question-guard.ts` — 생성된 질문에서 나이·성별·결혼/출산·가족·종교·
    출신·외모·정치·병력 주제를 걸러낸다. 걸린 질문은 **재생성하지 않고 버린다**
    (질문이 하나 적은 면접보다 불법 질문이 하나 뜨는 편이 훨씬 나쁘다).
  - 구현: `src/llm/input-moderation.ts` — 공고·자소서에 지시를 덮어쓰려는 문구가
    있으면 세션 생성 전에 422로 거부한다. 오탐이 인젝션을 놓치는 것보다 나쁘므로
    **명시적 지시 무효화 문구만** 잡는다.
- **직무 가중치 검산**: LLM이 반환한 weighted sum을 서버가 재계산해 신뢰.
- **프롬프트 버전 관리**: 프롬프트도 코드로 버전 태깅(품질 A/B·회귀 대비).
