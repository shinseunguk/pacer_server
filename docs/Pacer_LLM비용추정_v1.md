## ⚠️ 이 문서는 추정치였다 — 일부는 실측으로 대체됨 (2026-08-21)

작성 당시에는 API 키가 없어 **문자 수 → 토큰 환산 가정**(한국어 1자 ≈ 1.5토큰)에 기반했다.
어댑터(#32)를 붙이고 실제 호출을 돌려 아래를 실측했다. 나머지 절(§3~§7)의 금액은
**여전히 추정이며**, 실측이 쌓이는 대로 갱신한다.

### 실측 1회 (2026-08-21, Opus 5, 5문항 면접)

| 메서드 | 호출 | 입력 | 출력 | 비용 |
|--------|------|------|------|------|
| `evaluate` | 1 | 2,301 | 5,104 | **$0.148** |
| `generateQuestions` | 1 | 220 | ~1,000 | $0.028 |
| `decideNextTurn` | 3 | 324 | 398 | $0.024 |
| **면접 1회 합계** | 5 | | | **$0.200** |

> ⚠️ **이 면접은 5문항 중 4개를 스킵했다.** 답변이 다 채워지면 대화록이 길어져
> `evaluate` 입력이 크게 늘고, 꼬리질문도 더 붙는다.
> **추정치 $0.33은 낙관적일 가능성이 높다** — 절반만 답한 면접이 이미 $0.20이다.

### 메서드별 모델 실측 (2026-08-21) — ADR 0008

`decideNextTurn` 호출 1회 평균:

| | Opus 5 | Haiku 4.5 |
|---|---|---|
| 비용 | $0.01688 | **$0.00247** (−85%) |
| 지연 | 9.8초 | **3.6초** (−63%) |

면접당 절감: 5문항 $0.11 · 10문항 $0.22 · 15문항 $0.32.
`decideNextTurn`은 **답변마다** 나가서 10문항이면 15회 안팎이다.

> `generateQuestions`를 Sonnet 5로 내리는 건 보류했다. **Sonnet 5의 최소 캐시 길이가
> 1,024토큰인데 우리 프리픽스는 812토큰이라 캐싱이 꺼진다.** 토큰 단가는 40% 싸지만
> 캐시 절감(24%)을 잃어 실이득이 줄어든다.

### 실측으로 확인된 것

- **`evaluate`가 비용의 74%를 차지한다.** 대화록 전체를 입력으로 받고 모범답안까지
  생성하므로 출력 토큰이 압도적이다. 강등을 검토한다면 여기가 아니라
  `generateQuestions`·`decideNextTurn`부터다 (ADR 0004와 같은 결론).
- **`thinking`은 adaptive로 두었고, 위 호출들에서 thinking 토큰은 출력에 합산된다.**
- **프롬프트 캐싱은 프리픽스 구조를 고치기 전까지 적중률이 0이었다** — §5 참조.

## 2. 호출 구조 — 면접 1회 = LLM 12콜

코드 기준(`interviews.service.ts` `MAX_FOLLOW_UP = 2`, `create-interview.dto.ts` `questionCount` 3~10).

**대표 시나리오**: `questionCount = 5`(앱 기본), 기본 질문당 꼬리질문 평균 1회 → 답변 10회.

| 호출 (`InterviewEngine` 메서드) | 횟수 | 입력 | 출력 |
|------|------|------|------|
| `generateQuestions` | 1 | 가드레일+시스템 900자 + 공고 2,000자 + 지원자정보 1,000자 ≈ **3,900자** | 질문 5개 JSON ≈ **700자** |
| `decideNextTurn` | 10 | 가드레일+시스템 600자 + 직전 질문·답변 500자 ≈ **1,100자/회** | 판단 JSON ≈ **120자/회** |
| `evaluate` | 1 | 시스템 900자 + 전체 대화록 3,600자 ≈ **4,500자** | 점수·판정근거·**모범답안 5개** ≈ **3,000자** |
| **합계** | **12** | **≈ 19,400자 ≈ 29,100토큰** | **≈ 4,900자 ≈ 7,350토큰** |

**주의할 특성 두 가지**

- `decideNextTurn`이 **호출 횟수의 83%**(10/12)를 차지하지만, 개별 호출은 작고 판단은 단순하다.
- `evaluate`의 **출력**이 전체 비용의 큰 몫을 차지한다. 대부분이 **모범답안 5개**이며,
  출력 토큰은 **캐싱으로 절감할 수 없다**.

## 4. 모델 선택 (Phase A 결정)

**결정: 세 호출 모두 `claude-opus-5`. 비용은 모델 강등이 아니라 `effort`로 조절한다.**

| 메서드 | 모델 | `effort` | 근거 |
|--------|------|----------|------|
| `generateQuestions` | `claude-opus-5` | `high` | 세션당 1회. 질문 품질이 곧 서비스 품질 |
| `decideNextTurn` | `claude-opus-5` | **`low`** | 호출은 가장 많으나 "파고들까/넘어갈까" 이진 판단 |
| `evaluate` | `claude-opus-5` | `high` (필요시 `xhigh`) | 평가 일관성 = MVP 핵심 가설 |

### 왜 Phase A에서 최고 티어인가

Phase A의 목적은 비용 최적화가 아니라 **면접·평가 품질 검증**이다 (`Pacer_MVP범위_v1.md` §7).
최고 티어에서 먼저 기준선을 잡아야, 이후 모델을 내렸을 때 품질 저하의 원인이
**모델인지 프롬프트인지 구분**할 수 있다. 반대 순서로 가면 원인을 짚지 못한다.

최고 티어에서도 평가가 납득되지 않으면 그것은 프롬프트·루브릭 설계 문제라는 신호이며,
그 자체가 Phase A가 얻어야 할 정보다.

### 강등 판단 기준 — 지금이 아니라 데이터가 쌓인 뒤

- **판정 지표**: 리포트 만족도(👍 비율). 수집 API는 이미 있다 (issue #15).
- **1순위 후보**: Sonnet 5 (면접당 $0.33 → $0.20). 만족도 차이가 없으면 전환한다.
- **`decideNextTurn` 전용 후보**: Haiku 4.5. 단, `effort: low`를 먼저 시도한다 —
  모델이 같으면 톤·판단 기준이 일관되고 되돌리기 쉽다.
- **`evaluate`는 강등하지 않는다.** 평가 일관성이 서비스의 존재 이유다.

### 혼합 구성 (참고)

`generateQuestions`·`evaluate`는 Opus 5, `decideNextTurn`만 Haiku 4.5로 내린 경우:

| 메서드 | 모델 | 비용 |
|--------|------|------|
| `generateQuestions` | Opus 5 | $0.056 |
| `decideNextTurn` | Haiku 4.5 | $0.026 |
| `evaluate` | Opus 5 | $0.146 |
| **합계** | | **$0.23** (전량 Opus 5 대비 **31% 절감**) |

## 5. 프롬프트 캐싱 — 현재 설계에서는 효과가 작다

`Pacer_AI프롬프트설계_v1.md` §4의 `decideNextTurn`은 전체 대화록이 아니라
`baseQuestion + userAnswer`만 받는 **stateless 구조**다. 따라서 세션 내에서 반복 재사용되는
접두사는 **가드레일 + 시스템 프롬프트(약 600자 ≈ 900토큰)** 뿐이다.

| 모델 | 최소 캐시 길이 | 900토큰 접두사 | 면접당 절감 |
|------|----------------|----------------|-------------|
| Opus 5 | 512 | ✅ 캐싱됨 | **약 $0.035** (입력 비용의 24%, 전체의 11%) |
| Sonnet 5 | 1,024 | ❌ 미달 — 조용히 캐싱 안 됨 | $0 |
| Haiku 4.5 | 4,096 | ❌ 미달 | $0 |

- 캐싱 효과를 키우려면 `decideNextTurn` 호출에 공고·지원자 정보를 접두사로 함께 실어
  세션 내내 재사용하는 구조로 바꿔야 하는데, **입력 토큰을 더 쓰는 방향**이라 득실 계산이 필요하다.
- **가드레일을 늘려 억지로 최소치를 넘기는 것은 본말전도다.** 하지 않는다.
- 배치 API(50% 할인)는 면접이 SSE 실시간 진행이라 **적용 불가**하다.

### 실측: 프리픽스 순서를 틀리면 적중률이 0이 된다 (2026-08-21)

어댑터 첫 구현은 안전 규칙을 시스템 프롬프트 **맨 뒤**에 두고 전체 블록에 `cache_control`을 걸었다.
결과는 **쓰기 3,447토큰 / 읽기 0** — 적중률 0%.

| | 원인 |
|---|---|
| 캐시는 **프리픽스** 기준 | 앞부분(직무·문항 수 등 가변값)이 호출마다 달라 공유될 수 없었다 |
| 안전 규칙만으로는 **375토큰** | Opus 5 최소치 512에 미달 — 앞으로 옮겨도 여전히 캐싱 안 됨 |

**쓰기 요금은 입력가의 1.25배**라, 이 상태는 캐싱을 끄는 것보다 나빴다.

고친 방법: 불변 블록(안전 규칙 + 메서드별 공통 지시)을 **맨 앞 별도 system 블록**으로 빼고
거기에만 캐시를 걸었다. 가변값은 뒤 블록으로 분리했다.

| 프리픽스 | 토큰 | 캐시 |
|---|---|---|
| `questionSetPrefix` | 812 | ✅ |
| `nextTurnPrefix` | 645 | ✅ |
| `evaluationPrefix` | 855 | ✅ |

실측 절감: `generateQuestions` 호출이 $0.0284(쓰기) → **$0.0216(읽기)** 로 **24% 감소**.

> 교훈: `cache_control`을 걸었다고 캐싱되는 게 아니다. **적중률을 관측하지 않으면
> 요금만 더 내고 있는 상태를 알아챌 수 없다.** 대시보드(#35)에 캐시 적중률을
> 넣어둔 것이 이 문제를 드러냈다.

## 6. 유닛 이코노믹스 — Phase B 한도가 위험하다

`FREE_DAILY_QUESTION_LIMIT = 20`(기본 질문 기준, 꼬리질문 제외) = **5문항 면접 하루 4회**.
한도를 매일 소진하는 사용자는 **월 120회**.

| 모델 | 헤비 유저 월 원가 |
|------|-------------------|
| **Opus 5** | **$39.5** |
| 혼합 | $27.3 |
| Sonnet 5 (정가) | $23.8 |
| Haiku 4.5 | $7.9 |

구독가를 ₩9,900~19,900(약 $7~15)로 가정하면 **Opus 5 전량 사용 시 헤비 유저 1인당 월 $25~33 적자**다.

이는 `Pacer_MVP범위_v1.md` §5의 "LLM 비용: 무료 20질문 × 사용자 규모의 유닛 이코노믹스 사전 점검"
리스크가 **실재함을 확인한 것**이다. Phase B 진입 전 다음 중 하나 이상이 필요하다.

1. **하루 한도 하향** (20 → 10이면 헤비 유저 월 원가 절반)
2. **`decideNextTurn` 모델 강등** (혼합 구성, 31% 절감)
3. **모범답안을 지연 생성** — `evaluate` 출력의 대부분이며 전체의 약 34%.
   리포트 첫 화면에서 빼고 사용자가 펼칠 때 생성하면 실제 열람률만큼만 과금된다.
4. **구독가 상향** 또는 티어 분리

> 출력 토큰은 캐싱으로 줄일 수 없으므로 **3번이 구조적으로 가장 효과가 크다.**

## 8. 재측정 트리거

다음 중 하나라도 발생하면 이 문서를 갱신한다.

| 트리거 | 조치 |
|--------|------|
| **API 키 확보** | `count_tokens`로 대표 프롬프트 3종 실측 → 환산비 교체, §"추정치다" 경고 제거 |
| Anthropic 단가 개정 | §1 표와 기준일 갱신, 이하 금액 재계산 |
| 모델 변경 (`llm.module.ts`) | §3·§4 재계산, 최소 캐시 길이 재확인 (§5) |
| `effort` 변경 | 출력 토큰이 바뀌므로 재측정 |
| 프롬프트 대폭 변경 | §2 문자 수 재산정 |
| 토큰 사용량 로깅 도입 | **실측치로 전면 교체** — 추정 섹션을 실측으로 대체 |
| Sonnet 5 인트로 종료 (2026-08-31) | 인트로 행 삭제 |

### 실측 방법 (키 확보 후)

`count_tokens`는 모델별로 결과가 다르므로 **실제 사용할 모델 ID로** 호출한다.

```ts
const res = await client.messages.countTokens({
  model: 'claude-opus-5',
  system: GUARDRAIL + QUESTION_SET_SYSTEM,
  messages: [{ role: 'user', content: representativeJobPosting }],
});
// res.input_tokens
```

대표 프롬프트 3종(`generateQuestions` / `decideNextTurn` / `evaluate`)을 각각 재고, §2의
"문자 수 → 토큰" 열을 실측값으로 교체한다.

## 9. 프롬프트 설계 문서와의 충돌 (별도 처리 필요)

비용 검토 중 확인된 사항으로, `Pacer_AI프롬프트설계_v1.md`가 **현재 모델에서 쓸 수 없는 방식**을 규정하고 있다.
